Data

Action

01 / My Approach

Self-taught.
Evidence-led.

I learn AI security by studying real architectures and reducing them to concrete security questions: who can access an object, how permissions survive retrieval, what untrusted context can influence, where tools receive authority, how secrets cross service boundaries, and how failures are detected and recovered.

My current learning system uses a 40-mission security catalog covering application security, RAG and agent security, authentication and authorization, MCP and agent-to-agent boundaries, sandboxing, data protection, software and model supply chains, evaluation, observability, incident response, model-security specialties and secure delivery.

I keep source review, local fixtures, model experiments and real operating experience separate. A design or planned test is not presented as a production result.

03 / Working Method

From source
to evidence.

The goal is not to collect tool names. The goal is to understand the mechanism, test the responsible boundary and transfer the reasoning to a different architecture.

  1. 01

    Inspect

    Pin the source, configuration, identity model and relevant feature.

  2. 02

    Trace

    Follow identity, data and authority to the service that owns the decision.

  3. 03

    Predict

    Write legitimate, denied and failure outcomes before attempting a test.

  4. 04

    Attempt

    Use bounded synthetic fixtures or an explicitly authorized local environment.

  5. 05

    Observe

    Preserve raw requests, responses, logs, hashes, versions and side effects.

  6. 06

    Explain

    Connect the observed result to the source and separate native, configuration and fixture behavior.

  7. 07

    Improve

    Place the control at the authoritative boundary and preserve legitimate behavior.

  8. 08

    Retest

    Verify the fix, failure handling, rollback, transfer and remaining limitations.
